# tongyun-git 产品需求（PRD）

状态：MVP 范围已定（2026-10-07），v2 为规划，未开工。需求 ID 一经发布保持不变；修改时在原条目上改并注明日期。

相关文档：[用户流程](user-flows.md) · [界面方向](design/ui-direction.md) · [线框图](design/wireframes.md) · [验收测试](testing/acceptance-tests.md) · [开发计划](plan.md) · [Git 底层决策](decisions/0001-git-backend.md)

## 1. 目标

做一个独立的桌面 Git 图形客户端：日常改代码、看 diff、挑着暂存、提交、切分支、看提交树、推拉，都在一个窗口里用键盘就能完成；AI 是自带的能力，不用另装插件。

对标对象是 IntelliJ IDEA 自带的 Git 面板（Commit 工具窗口、Log、分支弹窗、Push 对话框）。「比它好用」在本文中只指下面这些可核对的差异，不作为笼统目标：

| IDEA 现状（用户日常感受，部分为推测，见第 9 节） | tongyun-git 的做法 | 对应需求 |
| --- | --- | --- |
| 要先打开整个 IDE 和项目，非 IDE 管理的仓库（脚本、文档、agent 工作目录）用起来重 | 独立小应用，直接打开任意文件夹 | R-01 |
| 改动、diff、日志分在不同工具窗口，来回切 | 主界面同时看到改动列表、diff 和提交区，日志是同窗口的一个视图 | R-02、R-03、R-10 |
| 按行提交靠 diff 里的勾选框，鼠标操作为主 | diff 里键盘选行，空格暂存或取消，和 lazygit 一致 | R-05、R-16 |
| 执行了哪些 git 命令不透明（Console 标签藏得深） | 「操作日志」面板显示每条执行过的 git 命令和输出 | R-15 |
| AI 写提交信息要另装 AI Assistant 并订阅 | 自带，使用自己配置的 OpenAI 兼容接口（默认 KIE） | R-07 |

不做成 IDE，不做代码编辑器，不做代码托管平台（PR、Issue）的管理。

## 2. 用户与使用环境

- **主要用户（已知）**：阿橦本人。日常写 Java 后端，用 IDEA；同时让 Claude Code、Codex 等 agent 在多个仓库里改代码，需要随时看清它们改了什么并挑着提交。
- **后续用户（假设）**：同样以命令行 agent 为主力的个人开发者。仓库公开前不面向他们做任何承诺。
- **平台**：Windows 10+ x64、macOS 12+（universal）、Ubuntu 22.04 x64（AppImage / deb），与 tongyun-planner 一致。
- **前提**：机器上已安装 git（见决策 0001）；网络操作的认证由用户自己的 git 配置负责。

需求雷达（`/workspace/demand-radar/2026-10-07-github-opportunities.md` 第二节）的相关结论：

- AI 写提交信息已是红海且在变冷，上面四个 GUI 里三个已经内置。**本项目把它当作基本功能，不当卖点。**
- 「agent 改坏了能一键完整回滚」是 AI+Git 里最明确的空位：Claude Code 的 `/rewind` 不跟踪 Bash 改的文件，Codex 移除了 `/undo`（openai/codex #9203，👍473，仍 open）。这对应 v2 的 V2-07，是本项目最可能做出差异的方向。

## 4. 核心流程

一次完整的核心任务（详见 [用户流程](user-flows.md) F1）：

打开仓库 → 看改动列表 → 点文件看 diff → 按文件或按行暂存 → 点 AI 生成提交信息并修改 → 提交 → 推送。

失败和恢复要覆盖：不是 Git 仓库、找不到 git、hook 拒绝提交、AI 请求失败或超时、推送被拒（远端有新提交）、拉取产生冲突、认证失败。

## 5. MVP 需求

每条的验收条件写成「前提 → 动作 → 应观察到」。测试用例编号见 [验收测试](testing/acceptance-tests.md)。

### R-01 打开仓库

- 场景：用户通过「打开文件夹」、把文件夹拖进窗口、或从「最近仓库」列表打开。
- 规则：
  - 选中的目录或其上级是 Git 工作区时，打开该工作区根目录。
  - 不是 Git 仓库时提示「这个文件夹不是 Git 仓库」，不自动 `git init`。
  - 裸仓库不支持，给出提示。
  - 启动时检测 git 可执行文件及版本；找不到或低于最低版本时，显示安装指引和「手动指定路径」入口，其余功能不可用。
  - 最近仓库最多保存 20 个，路径不存在的条目显示为失效并可移除。
- 验收：
  1. 有效仓库的子目录 → 打开 → 标题栏显示仓库根目录名和当前分支。
  2. 普通文件夹 → 打开 → 显示上述提示，最近列表不新增该路径。
  3. 设置里把 git 路径改成不存在的文件 → 应用提示 git 不可用，打开仓库按钮不可用。
- 不做：克隆仓库、新建仓库、同时打开多个仓库标签（v2 再议）。

### R-02 改动列表

- 场景：打开仓库后，左侧显示当前工作区的改动。
- 规则：
  - 分组：已暂存、未暂存、未跟踪、冲突。同一文件可同时出现在已暂存和未暂存里。
  - 每项显示状态（新增、修改、删除、重命名、类型变化）和路径；重命名显示「旧路径 → 新路径」。
  - 支持平铺和按目录树两种显示，切换后记住选择。
  - 工作区文件变化后自动刷新（文件监听 + 窗口重新获得焦点时刷新）；`.git` 内部变化（比如命令行里提交了）也要刷新。
  - 子模块显示为一项，不展开，MVP 不提供子模块操作。
- 验收：
  1. 命令行里新建、修改、删除各一个文件 → 不操作应用 → 列表在刷新后显示三项，状态分别正确。
  2. 命令行里 `git add` 其中一个文件 → 该文件移到「已暂存」。
  3. 命令行 `git mv a b` → 显示一项重命名「a → b」。
- 不做：IDEA 式 changelist（多个改动分组），见 V2-03 的 shelve。

### R-03 查看 diff

- 场景：在改动列表或提交详情里选中一个文件，右侧显示 diff。
- 规则：
  - 支持统一视图和左右对比视图，切换后记住选择。
  - 按文件扩展名做语法高亮；行号显示旧、新两列。
  - 二进制文件不显示内容，显示「二进制文件，大小变化 X → Y」；图片（png、jpg、gif、webp、svg）可选显示前后预览（MVP 可选，排期不够就砍）。
  - 超大 diff（阈值待 M1 定，暂定单文件超过 1 MB 或 5000 行变化）先显示摘要和「仍然加载」按钮。
  - 可切换「忽略空白」；文件换行符变化（CRLF ↔ LF）要显示提示，不能显示成整文件全部改动却不说明原因。
  - 未暂存文件的 diff 是「工作区对 index」，已暂存文件的 diff 是「index 对 HEAD」，标题上标明。
- 验收：
  1. 修改一个 `.java` 文件的两处 → 选中 → 看到两个 hunk、语法高亮、新旧行号。
  2. 只把一个文件的换行符从 LF 改成 CRLF → 选中 → 显示换行符变化提示。
  3. 修改一个 png → 选中 → 显示二进制提示，不卡死、不显示乱码。
- 不做：在 diff 里直接编辑文件。

### R-04 按文件暂存和取消暂存

- 场景：在改动列表中勾选文件，或选中后按空格。
- 规则：
  - 支持多选（Shift / Ctrl 或 Cmd）后一起暂存或取消。
  - 删除的文件暂存后在「已暂存」中显示为删除。
  - 冲突文件暂存即视为标记已解决（和 `git add` 一致），操作前确认一次。
- 验收：
  1. 选中两个未暂存文件 → 按空格 → 两个文件出现在「已暂存」，`git diff --cached --name-only` 输出这两个文件。
  2. 在「已暂存」里选中其中一个 → 按空格 → 它回到「未暂存」，命令行验证一致。

### R-05 按 hunk、按行暂存和取消暂存

- 场景：在未暂存文件的 diff 里选中一个或多个 hunk、一行或连续多行，暂存它们；在已暂存文件的 diff 里反向取消。
- 规则：
  - 选择方式：鼠标点行号区（Shift 扩选），或键盘上下移动、`Shift` 扩选；`a` 选中当前 hunk（和 lazygit 一致）。
  - 按空格或点「暂存所选」执行。只改 index，不改工作区文件内容。
  - 选中删除行和新增行的任意组合都要得到正确结果；未选中的新增行不进入 index，未选中的删除行在 index 中保留。
  - 未跟踪的新文件也可以只暂存部分行。
  - 二进制文件、子模块、换行符整体变化的文件只能按整文件暂存，按行选择不可用并说明原因。
  - 文件在选择后被外部修改时，暂存前重新计算 diff；对不上则取消操作并提示「文件已变化，请重新选择」。
- 验收：
  1. 某文件有 3 个 hunk → 只选第 2 个 → 暂存 → `git diff --cached` 只包含第 2 个 hunk，工作区文件内容不变。
  2. 一个 hunk 里有 2 行删除、3 行新增 → 只选第 1 行删除和第 2 行新增 → 暂存 → `git diff --cached` 与预期补丁逐字一致。
  3. 在已暂存 diff 里选中一行 → 取消暂存 → 该行回到未暂存 diff，其他已暂存内容不变。
  4. CRLF 文件做第 2 条操作 → 结果一致，index 里该文件的换行符没有被改变。
- 不做：在暂存时修改行内容（IDEA 的「编辑后提交」）。

### R-06 提交

- 场景：在提交区写提交信息，提交已暂存的改动。
- 规则：
  - 提交信息分标题和正文；标题超过 72 个字符时提示（不阻止）。
  - 没有已暂存改动或信息为空时，提交按钮不可用。
  - 用系统 git 执行提交，pre-commit、commit-msg hook 和用户配置的签名照常生效（决策 0001）。
  - hook 失败：显示 hook 的输出，提交信息保留，暂存状态不变。
  - 没配 `user.name` / `user.email` 时，提示用户按 git 的方式配置（显示命令），不由应用代写全局配置。
  - 提交成功后清空提交信息，刷新改动列表和日志。
  - 未提交的提交信息草稿按仓库保存，关掉应用再打开还在。
- 验收：
  1. 暂存一个文件、写信息 → `Ctrl/Cmd+Enter` → `git log -1` 显示该信息，改动列表只剩未暂存部分。
  2. 夹具仓库装一个必定失败的 pre-commit hook → 提交 → 显示 hook 输出，信息框内容不变，`git log` 没有新提交。
  3. 写一半信息后退出应用 → 重新打开同一仓库 → 草稿还在。
- 不做：amend（修改上一次提交）、多作者、提交模板编辑。amend 是否加入 MVP 见第 8 节问题 Q2。

### R-07 AI 写提交信息

- 场景：在提交区点「AI 生成」（或快捷键），根据已暂存的改动生成提交信息。
- 规则：
  - 发送内容：已暂存的 diff（截断到上限，默认 2 万字符，可设置）、改动文件列表、当前分支名、最近 10 条提交标题（用来学风格）。
  - 默认排除不发送的文件（只发送「该文件有改动」）：`.env*`、`*.pem`、`*.key`、`id_rsa*`、`*.p12`、`*secret*`，以及用户在设置里追加的规则。
  - 第一次使用时弹窗说明会把上述内容发送给哪个接口（显示 base URL），用户确认后才发送；可在设置里关闭 AI。
  - 接口：OpenAI 兼容的 chat completions。base URL、模型名、key 都在设置里配置，默认填 KIE。KIE 的接口路径把模型放在路径里（`https://api.kie.ai/<模型>/v1/chat/completions`），标准 OpenAI 兼容服务是 `<base>/v1/chat/completions`，所以设置里提供「请求地址模板」，内置 KIE 和标准两种预设。key 的来源依次为：环境变量 `KIE_API_KEY` → 系统钥匙串里保存的 key。key 只在 Rust 侧使用，不传给前端，不写入日志、配置文件或仓库。
  - 语言：设置项「跟随仓库最近提交 / 中文 / English」，默认跟随。可选「Conventional Commits 格式」。
  - 生成结果逐步显示在信息框里；用户可以随时停止。信息框原来有内容时，先放到撤销历史里，`Ctrl/Cmd+Z` 能恢复。
  - 失败（无 key、网络错误、超时 30 秒、接口报错）：显示一句原因和「去设置」入口，信息框原内容不变。
  - 没有已暂存改动时按钮不可用。
- 验收：
  1. 配好 key，暂存改动 → 点 AI 生成 → 30 秒内信息框出现非空的提交信息，可编辑后提交。
  2. 暂存一个 `.env` 文件和一个普通文件 → 用抓包或测试替身接口检查请求体 → 请求里只有 `.env` 的文件名，没有其内容。
  3. 不配置 key → 点 AI 生成 → 显示「未配置 AI 接口 key」和设置入口，没有发出网络请求。
  4. 测试替身接口 40 秒才响应 → 30 秒时显示超时，原内容保留。
  5. 全仓库搜索、应用配置目录和日志文件中都找不到 key 的明文。

### R-08 切换分支

- 场景：从分支弹窗（标题栏分支名或快捷键打开）选择分支切换。
- 规则：
  - 列出本地分支、远程分支，可输入过滤；显示每个本地分支相对上游的领先、落后数。
  - 选远程分支时，若本地没有同名分支，创建跟踪分支并切换。
  - 工作区改动会被切换覆盖时，git 会拒绝；应用显示冲突的文件列表和「取消」，不提供强制切换（MVP 不做 stash，见 V2-03）。
  - 处于合并或 rebase 进行中时，切换不可用并说明原因。
- 验收：
  1. 干净工作区 → 切到另一个本地分支 → 标题栏分支名变化，`git branch --show-current` 一致。
  2. 选 `origin/feature-x`（本地无同名）→ 切换 → 新建本地 `feature-x` 并跟踪 `origin/feature-x`。
  3. 修改一个在目标分支上内容不同的文件 → 切换 → 显示被阻止的文件列表，当前分支不变，改动不丢。

### R-09 新建分支

- 场景：在分支弹窗点「新建分支」，或在日志里右键某个提交「从这里新建分支」。
- 规则：
  - 起点默认当前 HEAD；从日志新建时起点为所选提交。
  - 名称按 `git check-ref-format --branch` 的规则实时校验；同名分支已存在时提示。
  - 「创建后切换」默认勾选。
- 验收：
  1. 输入 `feature/login` → 创建 → 新分支存在且已切换。
  2. 输入 `bad..name` → 创建按钮不可用并显示原因。
  3. 在日志选中三个提交以前的提交 → 从这里新建 → 新分支指向该提交。

### R-10 提交树图（日志）

- 场景：切到「日志」视图查看提交历史。
- 规则：
  - 每行显示：图形（分叉合并的线）、引用标签（本地分支、远程分支、标签、HEAD）、标题、作者、时间、短哈希。
  - 范围切换：全部分支 / 当前分支。
  - 过滤：按标题、作者、哈希前缀筛选。
  - 选中提交显示详情：完整信息、父提交、改动文件列表；点文件显示只读 diff（复用 R-03）。
  - 大仓库分批加载，滚动时补充；首屏加载时间和流畅度目标见 N-01。
  - 右键菜单 MVP 只有：复制哈希、从这里新建分支（R-09）。
- 验收：
  1. 夹具仓库有一次分叉再合并 → 日志显示两条线汇合，合并提交有两个父提交。
  2. 过滤输入某作者名 → 只显示该作者的提交。
  3. 选中某提交 → 点其中一个文件 → 显示该提交对该文件的 diff。
  4. 5 万条提交的夹具仓库 → 打开日志 → 首屏显示并可滚动到底部，期间界面不冻结（具体耗时记录为基线）。
- 不做：在日志里 cherry-pick、revert、reset、交互式 rebase（V2-02）。

### R-11 拉取（fetch / pull）

- 场景：工具栏「拉取」或快捷键；可单独「获取（fetch）」。
- 规则：
  - fetch：`git fetch --prune` 当前仓库所有远程，完成后刷新领先、落后数。
  - pull：仓库已配置 `pull.rebase` 或 `pull.ff` 时照用户配置执行；未配置时第一次拉取弹窗选择「合并 / 变基」，按仓库记在应用设置里（不改用户的 git 配置）。
  - 显示进度，可取消（终止 git 进程，提示取消后可能需要重新拉取）。
  - 出现冲突：改动列表显示「冲突」分组，顶部横幅显示「合并（或变基）进行中，有 N 个冲突」，提供「用外部编辑器打开」「标记已解决（暂存）」「中止合并 / 中止变基」。三栏合并界面在 V2-01。
  - 认证失败或网络失败：显示 git 输出的关键一行和完整输出入口；不在应用里输入或保存密码（`GIT_TERMINAL_PROMPT=0`，交给 credential helper）。
- 验收：
  1. 本地落后远程 2 个提交、无本地改动 → 拉取 → 本地与远程一致，日志更新。
  2. 本地和远程改了同一行 → 选「合并」拉取 → 显示冲突横幅和冲突文件；点「中止合并」→ 仓库回到拉取前状态（`git status` 干净，HEAD 不变）。
  3. 远程地址指向需要认证但无凭据的地址 → 拉取 → 30 秒内显示认证失败，应用不卡住。

### R-12 推送

- 场景：工具栏「推送」或快捷键，推送当前分支。
- 规则：
  - 推送前显示将推送的提交列表（领先上游的提交）和目标远程分支，确认后执行。
  - 当前分支没有上游时，默认目标为 `origin/<同名分支>` 并设置上游，用户可改远程名。
  - 被拒绝（远程有新提交）：提示「远程有新提交，请先拉取」并提供拉取按钮。MVP 不提供强制推送。
  - pre-push hook 失败：显示 hook 输出。
  - 推送标签不在 MVP。
- 验收：
  1. 本地领先 1 个提交 → 推送 → 远程裸仓库包含该提交，领先数归零。
  2. 新建本地分支（无上游）→ 推送 → 远程出现同名分支，本地分支的上游被设置。
  3. 远程先被别人推了新提交 → 推送 → 显示被拒提示和拉取按钮，本地不变。

### R-13 设置

- 内容：git 可执行文件路径、AI（开关、base URL、模型、key 存钥匙串 / 使用环境变量、语言、Conventional Commits、发送上限、排除规则）、主题（跟随系统 / 浅色 / 深色）、diff 默认视图、界面语言（MVP 只有中文，文案集中管理便于以后加英文）。
- 规则：设置保存在应用配置目录；key 不写入设置文件，只进系统钥匙串。
- 验收：
  1. 在设置里填 key 并保存 → 设置文件里没有 key，系统钥匙串里有对应条目，AI 生成可用。
  2. 主题切到深色 → 立即生效，重启后保持。

### R-14 最近仓库与窗口状态

- 规则：记住最近打开的仓库（R-01）、窗口大小位置、各面板宽度、上次打开的视图；重新打开时恢复。
- 验收：调整左栏宽度并退出 → 重新打开 → 宽度一致。

### R-15 操作日志与长操作

- 规则：
  - 应用执行的每条 git 命令行（R-06、R-11、R-12 等）记录命令、开始时间、耗时、退出码、输出，显示在可折叠的「操作日志」面板。命令行参数和输出里出现的 URL 凭据部分（`https://user:token@`）要打码。
  - 超过 1 秒的操作显示进度状态；网络操作可取消。
  - 同一仓库同时只允许一个写操作，其他写操作按钮在执行期间不可用。
- 验收：
  1. 执行一次推送 → 操作日志出现 `git push ...` 一条，含退出码和输出。
  2. 远程 URL 带 `user:token@` → 操作日志中显示为 `user:***@`。
  3. 推送进行中 → 提交按钮不可用，推送结束后恢复。

### R-16 键盘操作

- 规则：主要操作都有快捷键，默认值尽量与 IDEA 一致，方便肌肉记忆；可在设置中查看（MVP 不支持自定义）。

| 操作 | Windows / Linux | macOS |
| --- | --- | --- |
| 聚焦提交信息 / 打开提交区 | Ctrl+K | Cmd+K |
| 提交 | Ctrl+Enter（在信息框内） | Cmd+Enter |
| 推送 | Ctrl+Shift+K | Cmd+Shift+K |
| 拉取 | Ctrl+T | Cmd+T |
| 分支弹窗 | Ctrl+Shift+` | Cmd+Shift+` |
| 切到日志 / 改动 | Alt+9 / Alt+0 | Cmd+9 / Cmd+0 |
| 暂存或取消所选（文件、hunk、行） | 空格 | 空格 |
| 选中当前 hunk | a | a |
| AI 生成提交信息 | Ctrl+Alt+G | Cmd+Option+G |
| 命令面板 | Ctrl+Shift+P | Cmd+Shift+P |

- 验收：不用鼠标，完成 F1 核心流程（打开最近仓库除外）：选文件 → 进 diff 选行 → 暂存 → AI 生成 → 提交 → 推送。

### 非功能需求

- **N-01 性能**：没有已测基线，M0 用基准仓库实测后定阈值。先记录这些指标：冷启动到可操作；中等仓库打开到改动列表出现；改动 500 个文件时列表刷新；5 万条提交的日志首屏和滚动。界面线程不允许因 git 操作冻结（所有 git 调用都在 Rust 后台线程或子进程）。
- **N-02 安全与隐私**：
  - 不收集任何使用数据，不内置统计。
  - AI 只在用户触发时发送，发送范围见 R-07。
  - key 和 Git 凭据不出现在仓库、日志、设置文件、崩溃报告里。
- **N-03 数据安全**：MVP 不提供任何会丢失改动或改写远端历史的操作（reset --hard、clean、强制推送、丢弃改动）。唯一的「撤回」类操作是中止合并或变基，执行前确认一次。
- **N-04 平台**：见第 2 节。Linux 的文件监听、macOS 的钥匙串、Windows 的长路径（>260 字符）都要在验收里覆盖。

## 6. v2 规划（未排期）

建议顺序按差异化价值和需求证据排列，开工前各自补完整的需求条目。

| ID | 功能 | 一句话 | 关键规则草案 |
| --- | --- | --- | --- |
| V2-07 | 显示 agent 改过的文件并一键撤回 | 标出 Claude Code、Codex 等在某次会话里改过的文件，可整体或逐个撤回 | 来源可选：agent 的 hooks 日志（Claude Code PreToolUse / PostToolUse）、Codex 会话日志、会话期间的文件监听；撤回前先在 `refs/tongyun/snapshots/*` 打快照，撤回本身可再撤回；不动用户的 HEAD 和暂存区；Bash 删掉的文件也能恢复（快照覆盖工作区，含未跟踪文件，遵守 .gitignore 和大小上限）；只保证工作目录里的文件 |
| V2-01 | 三栏合并冲突 + AI 解释和方案 | 左（我方）中（结果）右（对方）三栏，AI 解释每个冲突块并给合并建议 | 建议需要用户逐块接受；接受后结果可编辑；全部解决后才能标记已解决；AI 请求范围与 R-07 相同的隐私规则 |
| V2-06 | 提交前 AI 审 diff | 提交前对已暂存改动做一次审查，列出可能的问题 | 只给建议，不阻止提交；可设为「每次提交前自动审」；结果按文件和行定位 |
| V2-08 | 多 agent 的 worktree 并排看 | 并排显示同一仓库多个 worktree 的改动和分支，提前提示改到同一文件或同一函数 | 新建、删除 worktree；预警基于文件和 hunk 重叠，先不做语义分析 |
| V2-03 | stash 和 shelve | stash 用 git 原生；shelve 是应用管理的补丁集（IDEA 概念），不进 git 历史 | shelve 存在仓库的 `.git/tongyun/shelf/`；可部分取回 |
| V2-04 | 文件历史和 blame | 某文件的提交历史、逐行 blame，点行跳到对应提交 | 大文件 blame 分段加载 |
| V2-02 | 交互式 rebase 拖拽 | 拖拽排序、合并（squash/fixup）、改信息、删除提交 | 只允许改未推送的提交，改已推送提交需二次确认；执行前自动打快照，失败可一键回到原状 |
| V2-05 | 自然语言问提交历史 | 比如「上周谁改了登录逻辑」 | 需求证据弱，最后做；先在本地检索提交信息和 diff 摘要，再交给 AI 总结 |

MVP 明确不做、v2 也暂不规划：克隆和新建仓库界面、PR / Issue 管理、Git LFS 管理界面、子模块操作、多窗口多标签、插件系统、自定义快捷键、英文界面。
